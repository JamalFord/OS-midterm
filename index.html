Multiprogramming Timeline Challenges Ch1 S12–15

  • Rule: Single CPU, multiprogramming without time-sharing ($p_1$ starts at $t=0$; $p_2$ starts CPU as soon as $p_1$ enters I/O).
  • Challenge 1 (1 Shared I/O Device, S13): $p_1(C=10, I/O=50)$, $p_2(C=30, I/O=60)$.
    • No Multiprogramming: $(10+50)+(30+60) = \mathbf{150}$.
    • With Multiprogramming (1 I/O dev): $p_1$ CPU $0\to 10$, I/O $10\to 60$. $p_2$ CPU $10\to 40$, waits for single I/O device $40\to 60$, then I/O $60\to 120 \implies \mathbf{120}$.
  • Challenge 2 (2 Separate I/O Devices, S15): $p_1(C=20, I/O=40)$, $p_2(C=10, I/O=80)$.
    • No Multiprogramming: $60+90 = \mathbf{150}$.
    • With Multiprogramming (2 I/O devs): $p_1$ CPU $0\to 20$, I/O₁ $20\to 60$. $p_2$ CPU $20\to 30$, I/O₂ $30\to 110$ (overlaps!) $\implies \max(60,110) = \mathbf{110}$.

1.2 Organization, Storage & Hardware Ch1 S20–26

  • OS Comparison Table (S20):
    • Windows 11: File system = NTFS | Kernel = Windows NT Hybrid
    • macOS: File system = APFS | Kernel = XNU Hybrid (Mach-influenced)
    • Linux: File system = ext4, Btrfs, XFS | Kernel = Monolithic, Modular
  • Device Chain (Note S23): Application → Kernel → Device Driver (OS software) → Device Controller (device hardware) → Physical Device.
  • Instruction Cycle (S24–25): 1. Fetch (at PC) → 2. Decode → 3. Execute → 4. Write Back / Update PC → 5. Check Events (interrupts at instruction boundary).
  • Memory Hierarchy (S22): Registers $\to$ L1/L2/L3 Cache $\to$ Main Memory (DRAM) [Volatile: lost on power off] $\to$ SSD / NVMe / Disk / Archive [Non-volatile / persistent].
  • Parallel Hardware (S26): Shared-Memory (1 address space, loads/stores, locks & cache coherence, multicore) vs. Distributed-Memory (private RAM per node, message passing over interconnect, clusters/cloud).

1.3 Dual-Mode & Privileged Instructions Ch1 S28–33

  • Hardware Mode Bit: User Mode (1) = unprivileged subset, restricted memory; Kernel Mode (0) = full hardware & memory access.
  • 4 Privileged Instruction Categories (S30):
    1. I/O Control (start/configure devices)
    2. Memory Control (modify page tables / protection)
    3. Interrupt Control (enable/disable interrupts)
    4. Processor Control (halt CPU or switch mode)
  • Illegal Attempt in User Mode: Hardware blocks execution, triggers a synchronous trap/exception into kernel mode, and OS terminates process or returns error.
  • Timer Protection (S31 Note): Before dispatching user code, kernel sets a hardware timer (privileged). Even in an infinite loop while(1);, timer expires & interrupts CPU back to kernel mode.

  • 5 Interrupt-Handling Steps (S38): 1. Event (HW detects request) $\to$ 2. Save (PC & minimal CPU state) $\to$ 3. Vector (locate handler via interrupt vector table) $\to$ 4. Handle (service cause in kernel) $\to$ 5. Return (restore state & resume).
  • 6 System Call Categories (S41): (1) Process control (fork, exec, exit, wait), (2) File mgmt (open, read, write, close), (3) Device mgmt (request, release, ioctl), (4) Info maintenance (time, PID, UID), (5) Communication (pipe, socket, shm), (6) Protection (chmod, chown).
  • API vs Wrapper vs Syscall (S42–45 Note): App calls C library wrapper (glibc read()) $\to$ puts syscall # in %rax & args in registers $\to$ executes syscall trap $\to$ kernel validates fd/buffer/permissions $\to$ if error, kernel returns negative code and wrapper sets errno & returns -1. (1 API call may invoke 0, 1, or many syscalls).
  • Mode Switch $\ne$ Context Switch (S46): Mode switch changes privilege (User $\leftrightarrow$ Kernel) for the same process. Context switch changes which process runs (saves $\text{PCB}_A$, loads $\text{PCB}_B$). Every syscall causes a mode switch, NOT necessarily a context switch!
  • System Call Forensics Quiz (strace): fd 0=stdin, fd 1=stdout, fd 2=stderr, fd 3+=first opened file (openat()=3). If openat()=-1 ENOENT, perror() writes to fd 2 (stderr) and exits early (no read/close). strace shows syscall names/args/returns/errno, NOT the CPU mode bit or context switches.

2.1–2.2 Process Memory, Lifecycle & PCB Ch2 S5–19

  • Address Space (Low $\to$ High Virtual Address, S6–7 Note):
    • Text (low): Read-only machine code instructions.
    • Data: Global & static variables (Initialized Data + BSS uninitialized/zero-filled globals).
    • Heap: Dynamic memory (malloc/new); grows UPWARD ($\uparrow$).
    • Stack (high): Function call frames, local vars, return addresses; grows DOWNWARD ($\downarrow$).
  • 5-State & 7-State Transitions (S12–15):
    • New --(admit)--> Ready --(dispatch)--> Running --(exit)--> Terminated
    • Running --(preempt / quantum expired)--> Ready
    • Running --(block on I/O or event)--> Waiting/Blocked --(wake/completion)--> Ready (NEVER Waiting $\to$ Running directly!)
    • Suspended States (S15): Waiting --(swap out)--> Blocked Suspended --(I/O finishes!)--> Ready Suspended --(restore to RAM)--> Ready.
  • 4 PCB Categories (S16–18): (1) Identity (PID, PPID, UID), (2) CPU Context (PC, registers, SP, flags), (3) State & Scheduling (state, priority, queue pointers), (4) Memory, I/O & Accounting (page tables, open fds, CPU time). S18 Quote: PC is the timestamp (next instruction); registers hold unfinished details.

2.3 Process Creation, fork/exec/wait, Zombie vs Orphan Ch2 S21–36

  • Creation Steps (S21 Note): Assign new PID $\to$ allocate PCB $\to$ allocate/setup address space $\to$ initialize CPU context & open file table $\to$ link into parent/child hierarchy & insert into Ready queue.
  • Priority Ready List Trace (`create` / `timeout`, S25–26):
    • Prio 2 (highest), 1, 0. Initial: $Q_2=[P_0^*]$. create(n) adds next PCB to tail of $Q_n$ (no preemption). timeout() moves running process to tail of its queue.
    • Sequence: 1. create(1) ($P_0\to P_1$ in $Q_1$) $\to$ 2. create(2) ($P_0\to P_2$ in $Q_2=[P_0^*, P_2]$) $\to$ 3. timeout() ($Q_2=[P_2^*, P_0]$; $P_2$ runs!) $\to$ 4. create(0) ($P_2\to P_3$ in $Q_0$) $\to$ 5. timeout() ($Q_2=[P_0^*, P_2]$; $P_0$ runs!) $\to$ 6. create(2) ($P_0\to P_4$ in $Q_2$).
    • Result: $P_0$ has 3 children ($P_1, P_2, P_4$); $P_2$ has 1 child ($P_3$); $P_1, P_3, P_4$ have 0 children.
  • `fork()` Return Values (S22/27): Returns < 0 on error; returns 0 in Child (get real PID via getpid()); returns > 0 (child's PID) in Parent. Uses Copy-on-Write (COW) page sharing until written.
  • `execvp()` & `_exit(127)` (S28–29 Note): execvp() replaces code/data/heap/stack in-place keeping the SAME PID (never returns on success). If it fails, child calls _exit(127) (avoids flushing duplicate parent stdio buffers; 127 = command not found). Parent collects status via waitpid(pid, &status, 0) + WIFEXITED(status) + WEXITSTATUS(status).
  • Zombie vs. Orphan (S33):
    • Zombie: Child is dead, parent hasn't called wait() yet; keeps PCB/process-table slot for exit status.
    • Orphan: Parent died first while child is still alive; kernel reparents child to init/systemd (PID 1) to reap it later.
  • Termination Cascade (`destroy(p)`, S34–36): Recursively kills all descendants in subtree, frees memory/files/locks, removes from queues (or leaves zombie until parent waits).

2.5–2.6 Threads, Mapping Models & Server Math Ch2 S45–66

  • Shared in Process vs. Private per Thread (TCB) (S47):
    • Shared: Text (code), Data/BSS (globals), Heap, Open files, Signals/WD.
    • Private per Thread (TCB): Thread ID, Program Counter (PC), CPU Registers, Stack, scheduling state/priority.
  • Server Caching Workout (S53–54): Arrivals every $25\text{ ms}$. Cache hit ($80\%$) = $15\text{ ms}$ CPU. Cache miss ($20\%$) = $15\text{ ms}$ CPU + $75\text{ ms}$ disk ($90\text{ ms}$ total). Thread creation cost = $10\text{ ms}$ CPU.
    • Single-threaded avg time: $0.8(15) + 0.2(15+75) = 12 + 18 = \mathbf{30\text{ ms}} > 25\text{ ms}$ (cannot keep up!).
    • Multi-threaded avg CPU time: $10\text{ ms (create)} + 15\text{ ms (work)} = \mathbf{25\text{ ms}}$ (overlaps disk wait $\implies$ keeps up!).
  • 4 Thread Mapping Models (S56–59):
    • Many-to-One (User-Level): Fast user-space switches; 1 blocking syscall blocks entire process; max 1 core (no parallelism).
    • One-to-One (Kernel-Level): 1 user $\to$ 1 kernel thread (Linux/Windows/macOS); true multicore parallelism; blocking syscall doesn't block peers; higher creation/switch cost.
    • Many-to-Many ($M:N$): $M$ user threads multiplexed on $N$ kernel threads.
    • Two-Level: $M:N$ pool + ability to bind critical user thread 1:1.
  • Linux `clone()` Task Model (S60 Note): Linux treats processes & threads as tasks (`task_struct`). fork() = minimal sharing; pthread_create() calls clone(CLONE_VM | CLONE_FILES | CLONE_THREAD).
  • Multithreaded `fork()` & `exec()` (S63): If child calls exec() right away, duplicate only calling thread (all other threads vanish at exec()).

2.7–2.9 Context Switching, TLB & Schedulers Ch2 S68–98

  • Context-Switch PCB Rule (S70–75 Note): While process $p$ is actively running on the CPU, $p$'s live state is in the CPU registers and $p$'s PCB copy is out-of-date! Only when an interrupt/trap enters the OS is $p$'s current CPU state saved into $p$'s PCB.
  • Who Can Trigger a Switch for Running $p$? (S77):
    • Process $p$ itself (blocks/exits) = TRUE | The OS (preemption) = TRUE | Another user process $q$ directly = FALSE!
  • Direct vs Indirect Switch Cost & TLB (S82–83 Note):
    • Direct cost: Saving/restoring registers, scheduler/dispatcher execution, updating memory pointers.
    • Indirect cost: Cold L1/L2/L3 caches, pipeline flush, TLB flush.
    • TLB (Translation Lookaside Buffer): Hardware cache in MMU storing VPN → PFN translations so virtual memory access avoids an extra RAM page-table lookup.
  • Schedulers & Dispatcher (S88):
    • Long-Term: Admits jobs from Job Queue $\to$ Ready (low freq; controls degree of multiprogramming).
    • Medium-Term: Swaps processes out/in (Blocked/Ready Suspended).
    • Short-Term (CPU): Picks next Ready process for CPU (very high freq).
    • Dispatcher: Switches context, switches to user mode, jumps to PC (time taken = dispatch latency).
  • Non-Preemptive Decision Points (S93): Decisions occur ONLY when running process blocks or terminates (NOT on new arrival in RL or wake from blocked $\to$ ready!).
  • I/O-Bound vs CPU-Bound (S94): Interactive OSes give higher priority to I/O-bound processes (short CPU bursts). CPU burst time = CPU execution time only (excludes I/O wait).
  • Core Scheduling Formulas (S96–98):
    • $\text{Turnaround Time (TAT)} = \text{Completion Time (CT)} - \text{Arrival Time (AT)}$
    • $\text{Waiting Time (WT)} = \text{TAT} - \text{Burst Time (BT)}$ (time in Ready queue)
    • $\text{Response Time (RT)} = \text{First CPU Start Time} - \text{AT}$
    • $\text{CPU Utilization} = \frac{\text{CPU Busy Time}}{\text{Total Elapsed Time}} \times 100\%$
    • $\text{Throughput} = \frac{\text{Completed Processes}}{\text{Total Elapsed Time}}$

2.10 Scheduling Algorithms & Slide Workouts Ch2 S100–149

  • Arbitration Rule (S106): Breaks ties among equal priorities (FIFO, SJF, lowest PID, RR); does NOT change priority values.
  • FCFS (S107–108): Non-preemptive FIFO. Suffers from Convoy Effect (short I/O-bound jobs stuck behind 1 long CPU-bound job).
    • Slide 108: $p_1(0,24), p_2(0,3), p_3(0,3) \implies$ Gantt: $p_1(0\text{–}24), p_2(24\text{–}27), p_3(27\text{–}30)$. $\text{Avg TAT} = \frac{24+27+30}{3} = \mathbf{27}$, $\text{Avg WT} = \frac{0+24+27}{3} = \mathbf{17}$.
  • Non-Preemptive Priority (S109–110, Lower # = Higher Prio):
    • $p_1(0,10,\text{prio }3), p_2(2,6,\text{prio }1), p_3(5,2,\text{prio }2)$. $p_1$ runs $0\text{–}10$; at $t=10$, $p_2(\text{prio }1)$ beats $p_3(\text{prio }2) \implies p_2(10\text{–}16), p_3(16\text{–}18)$. $\text{CT}=[10,16,18], \text{TAT}=[10,14,13] (\text{Avg }\mathbf{12.33}), \text{WT}=[0,8,11] (\text{Avg }\mathbf{6.33})$.
  • SJF (Non-Preemptive, S114–115): Optimal avg WT for non-preemptive.
    • $p_1(0,6), p_2(2,8), p_3(4,7), p_4(5,3) \implies p_1(0\text{–}6) \to p_4(6\text{–}9) \to p_3(9\text{–}16) \to p_2(16\text{–}24)$. $\text{TAT}=[6,22,12,4] (\text{Avg }\mathbf{11.0})$, $\text{WT}=[0,14,5,1] (\text{Avg }\mathbf{5.0})$.
  • SRTF (Preemptive SJF, S117–119): Preempts if new arrival's burst $<$ remaining time!
    • $p_1(0,8), p_2(1,4), p_3(2,9), p_4(3,5) \implies p_1(0\text{–}1) \to p_2(1\text{–}5) \to p_4(5\text{–}10) \to p_1(10\text{–}17) \to p_3(17\text{–}26)$. $\text{CT}=[17,5,26,10]$, $\text{TAT}=[17,4,24,7] (\text{Avg }\mathbf{13.0})$, $\text{WT}=[9,0,15,2] (\text{Avg }\mathbf{6.5})$.
  • Burst Prediction (Exponential Averaging, S113 Note):
    $$\tau_{n+1} = \alpha\, t_n + (1 - \alpha)\,\tau_n \quad (0 \le \alpha \le 1)$$
  • Priority Starvation & Aging (S121): Low-priority jobs can starve indefinitely; Aging gradually increases priority as wait time grows.

Round Robin (RR), MLFQ & Modern Schedulers Ch2 S122–149

  • RR Queue Rule (S124–126): New arrivals at or before $t$ join Ready Queue BEFORE the preempted process at time $t$ is re-queued!
    • Slide 126 Workout ($Q=4\text{ ms}$): $P_1(0,10), P_2(1,5), P_3(2,8)$.
    • Gantt: $P_1(0\text{–}4) \to P_2(4\text{–}8) \to P_3(8\text{–}12) \to P_1(12\text{–}16) \to P_2(16\text{–}17) \to P_3(17\text{–}21) \to P_1(21\text{–}23)$.
    • $\text{CT}: P_1=23, P_2=17, P_3=21$. $\text{TAT}=[23,16,19] (\text{Avg }\mathbf{19.33})$. $\text{WT}=[13,11,11] (\text{Avg }\mathbf{11.67})$.
  • RR Context-Switch Overhead Formulas (S128–129): Burst $=T$, Quantum $=Q$, Switch cost $=S$:
    • Case 1 ($T < Q$, finishes before quantum): $\text{Wasted Fraction} = \mathbf{\frac{S}{T + S}}$.
    • Case 2 ($T \gg Q$, many quanta per burst): $\text{Wasted Fraction} = \mathbf{\frac{S}{Q + S}}$.
    • As $Q \to \infty$, RR degenerates into FCFS; as $Q \to 0$, overhead $\to 100\%$.
  • 3-Queue MLFQ Workout (S135–138): $Q_0(\text{RR }8), Q_1(\text{RR }16), Q_2(\text{FCFS})$. $P_1(0,30), P_2(2,6), P_3(10,12)$.
    • $0\text{–}8: P_1(Q_0\to Q_1,\text{rem }22)$ | $8\text{–}14: P_2(Q_0,\text{finishes at }14!)$ | $14\text{–}22: P_3(Q_0\to Q_1,\text{rem }4)$ | $22\text{–}38: P_1(Q_1\to Q_2,\text{rem }6)$ | $38\text{–}42: P_3(Q_1,\text{finishes at }42!)$ | $42\text{–}48: P_1(Q_2,\text{finishes at }48!)$.
  • 4-Queue MLFQ Workout (S139–141): $Q_0(\text{RR }1), Q_1(\text{RR }2), Q_2(\text{RR }4), Q_3(\text{FCFS})$. $P_1(0,8), P_2(0,3), P_3(1,5)$.
    • $0\text{–}1: P_1(Q_0\to Q_1,\text{rem }7)$ | $1\text{–}2: P_2(Q_0\to Q_1,\text{rem }2)$ | $2\text{–}3: P_3(Q_0\to Q_1,\text{rem }4)$ | $3\text{–}5: P_1(Q_1\to Q_2,\text{rem }5)$ | $5\text{–}7: P_2(Q_1,\text{done at }\mathbf{7}!)$ | $7\text{–}9: P_3(Q_1\to Q_2,\text{rem }2)$ | $9\text{–}13: P_1(Q_2\to Q_3,\text{rem }1)$ | $13\text{–}15: P_3(Q_2,\text{done at }\mathbf{15}!)$ | $15\text{–}16: P_1(Q_3,\text{done at }\mathbf{16}!)$.
  • Multiprocessor & Modern Schedulers (S144–149):
    • Affinity: Soft (preferred CPU) vs. Hard (restricted CPU set) for warm caches.
    • NUMA: Local node RAM is faster than remote node RAM.
    • Real-Time: RMS (fixed prio: shorter period $\to$ higher prio) vs. EDF (dynamic: nearest deadline first, up to $100\%$ CPU).
    • Linux CFS vs EEVDF (S149): CFS picks smallest vruntime; EEVDF (Linux 6.6+) checks eligibility ($\text{lag} \ge 0$) & picks earliest virtual deadline.

3.1 Concurrency Foundations (★ Oct 7/8 Exam 1 Cutoff ★) Ch3 S1–21

  • Slide 21 Official Marker: "Exam1, end of the session for October 7, and 8".
  • Concurrent vs. Parallel (S6–7, 14–15):
    • Concurrency (Structuring/Progress): Multiple tasks make progress over overlapping time intervals (works on 1 core via time-sliced interleaving, or on multiple cores).
    • Parallelism (Execution): Multiple instructions execute at the exact same instant (requires $\ge 2$ cores or independent HW units like CPU + DMA I/O).
  • 1-Core I/O + Compute Overlap Workout (S8 & S17):
    • Task A: $2\text{ ms I/O wait} + 1\text{ ms CPU}$. Task B: $2\text{ ms CPU}$.
    • Sequential (Wait-then-Run): $2 + 1 + 2 = \mathbf{5\text{ ms}}$ (CPU utilization $= 3/5 = \mathbf{60\%}$).
    • Concurrent (Overlap B's CPU during A's I/O): $t=0\text{–}2$: A waits I/O while B runs $2\text{ ms}$ CPU; $t=2\text{–}3$: A runs $1\text{ ms}$ CPU $\implies \mathbf{3\text{ ms}}$ total! (CPU utilization $= 3/3 = \mathbf{100\%}$).
  • Stack Variable Pointer Warning (S9–10 Note): A thread's stack is private by convention, NOT hardware-isolated from other threads in the same process! If Thread A passes &x (address of its stack variable) to Thread B, Thread B CAN read/modify A's x!
  • Shared Counter Lost-Update Trace (S11, 18–20):
    • counter++ compiles to 3 machine steps: r = counter; r = r + 1; counter = r; (where counter is shared, but rA and rB are private registers).
    • If counter = 10 and both A and B read 10 before either stores back, both write 11 $\implies$ final value is 11 instead of 12 (Lost Update)!
    • Even with a mutex, which thread enters first is nondeterministic (A then B, or B then A), but the final value is deterministically 12.
  • 4 Core Concurrency Hazards (S12–13): (1) Race Condition / Data Corruption, (2) Deadlock (cycle of mutual waiting), (3) Starvation (runnable task repeatedly denied progress), (4) Lost Wakeup (check condition & sleep not atomic).

3.2–3.4 Critical Sections, Peterson's & Atomics Ch3 S23–57

  • Data Race vs. Race Condition (S23 & 31):
    • Data Race: Unsynchronized concurrent accesses to 1 memory location by $\ge 2$ threads where $\ge 1$ writes (undefined behavior in C/C++).
    • Race Condition: Correctness depends on timing/interleaving (can happen even WITH atomic operations, e.g., check-then-act if (seats > 0) seats--;).
  • 3 Critical-Section Requirements (S27–28):
    1. Mutual Exclusion (Safety): At most 1 thread inside CS at any time.
    2. Progress (Liveness): If CS is empty, decision among entering threads cannot be postponed indefinitely; threads in Remainder Section cannot block entry.
    3. Bounded Waiting (Liveness): Bound on how many times others can overtake a waiting thread.
  • Broken Attempts (S34–35):
    • Strict Alternation (turn): Satisfies Mutual Exclusion, FAILS Progress (if $T_1$ is in Remainder, $T_0$ cannot enter twice in a row).
    • Flags Only (flag[i]=true): Both set flags true & wait forever $\implies$ Deadlock (fails Progress).
  • Peterson's Algorithm (S37–41):
    flag[i] = true; turn = j; while (flag[j] && turn == j); /* CS */ flag[i] = false;
    • Contention Trace (S38): If $T_0$ sets turn=1 then $T_1$ sets turn=0, the last write (`turn=0`) wins $\implies T_0$ sees turn != 1 and $T_0$ enters CS first! Max overtakes $= \mathbf{1}$.
    • Modern CPU Caveat (S40–41): Store buffers can reorder flag[i]=true after reading flag[j]; requires a memory fence/barrier! Also note: C volatile prevents compiler caching, NOT hardware races or reordering (S55).
  • Hardware Atomics (S47–53):
    • test_and_set(&L): Sets L=true, returns old value. Lock: while(test_and_set(&L));.
    • compare_and_swap(&x, expected, desired): Updates x=desired iff x==expected.
    • Spinlock vs Sleeping Mutex (S51–52): Spinlocks never sleep on 1 core (waste full quantum) and lack bounded waiting; use spinlocks only for very short multicore kernel holds.

3.5–3.8 Semaphores, Monitors, Classics & Amdahl Ch3 S59–111

  • Mutex vs. Binary Semaphore vs. Counting Semaphore (S60–67):
    • Mutex: Has strict ownership (only locker can unlock).
    • Binary Semaphore (0/1): No ownership (Thread A can signal to wake Thread B).
    • Counting Semaphore ($N$): Tracks $N$ available resource instances.
    • Initial Values (S67): Mutual exclusion = 1; Pool of $K$ resources = K; Wait for event ($A \prec B$) = 0.
  • Monitors & Condition Variables (S69–74):
    • wait(cv, m) atomically releases mutex `m` and sleeps, then reacquires `m` before returning. Signals with no waiters are not stored!
    • Mesa vs. Hoare (S74): In Mesa monitors (POSIX/Java), signaler keeps running and another thread can barge in & change state before awakened thread runs $\implies$ ALWAYS use `while (!predicate) wait(cv, m);` (NEVER `if`)! (Hoare hands off lock immediately).
  • 3 Classical Synchronization Problems (S80–92):
    • Bounded Buffer: empty=N, full=0, mutex=1. Producer: wait(empty) → wait(mutex) → put → signal(mutex) → signal(full). (Reversing wait(mutex) before wait(empty) causes DEADLOCK!).
    • Readers–Writers: 1st reader (readers==1) calls wait(room); last reader (readers==0) calls signal(room). (Reader-preference can starve writers).
    • Dining Philosophers: All 5 grab left fork $\implies$ deadlock! Fix via (1) Global Fork Ordering (last philosopher picks higher/lower index first), (2) max 4 at table, or (3) monitor.
  • Priority Inversion & Amdahl's Law (S101–105):
    • Priority Inversion: Medium task $M$ preempts Low task $L$ while $L$ holds lock needed by High task $H$. Fix: Priority Inheritance Protocol ($L$ inherits $H$'s priority until unlock).
    • Amdahl's Law (S105): Serial fraction $s$, cores $p$: $$\text{Speedup}(p) \le \frac{1}{s + \frac{1 - s}{p}}, \qquad \lim_{p\to\infty}\text{Speedup} = \frac{1}{s}$$ Slide 105 Example ($s=0.20, p=4$): $\frac{1}{0.20 + 0.80/4} = \frac{1}{0.40} = \mathbf{2.5\times}$ (max at $\infty$ cores $= \mathbf{5\times}$).
